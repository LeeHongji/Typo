# 断网保护：网络不好时不丢字

## 1. 问题

2026-11-06 22:19 的一次实际记录：上传卡了 5.8 秒，火山返回 `45000081`，随后出错路径和恢复路径同时运行，会话被结束两次，录音条卡在「恢复中」。用户说的话丢了，或被贴进当时恰好在前台的窗口。

## 2. 原则

1. 实时流断开不等于听写失败：继续录音。
2. 一次会话只能由一条路径结束。
3. 文字只走正常的送达流程（锁定的输入框、引用、截图），不再有单独的「恢复中」阶段，也不往当前前台窗口贴。
4. 实在识别不出来，也要留下录音，之后能重新识别。

## 3. 行为

### 3.1 哪些错误算断流

`Protocol/VolcHeader.swift`：火山的 `45000081`（服务器等不到被卡住的音频而放弃）和 `55xxxxxx`（服务端繁忙或内部错误）属于断流，不是对账号的判定。连接阶段的网络失败同样处理。账号和请求类错误仍然立即结束会话并显示服务器的原话。

服务器随后的关闭帧不能再结束一次会话。

### 3.2 录音期间

断流后 `AppState.markConnectionLost` 把 `networkState` 设为 `.lost`，托盘提示连接已断开，录音继续。Typo 把手放到耳边听。

### 3.3 松手之后

结束音频和等待最终文字同时进行。等待跟着文字走：最后一次收到文字之后再等 2.5 秒，从松手算起最多 8 秒（`finalQuietWait`、`finalWaitCap`）。服务器已经沉默就不再等。

需要整段重识别的条件：实时流失败，并且上传失败、有流错误或没有可用的实时结果。此时：

1. `networkState` 变为 `.retrying`，录音条显示「正在用整段录音重新识别…」。
2. 用整段录音走批量识别。时间预算为 12 秒加上录音时长的 0.2 倍，上限 30 秒（`batchFallbackBudget`），原先是 90 秒。
3. 成功：结果走正常送达。
4. 失败：断流前已听到的文字仍送到锁定的输入框，结果为 `insertedPartial`，录音条给出警告，Typo 露出不好意思的表情。录音以 AAC 保存进历史，保留 7 天。
5. 一个字都没听到：仍保留录音并告知用户。

处理超过 3 秒时录音条显示「网络有点慢，还在等… Esc 取消」（`AppState.slowProcessingAfter`）。

### 3.4 从历史重新识别

`RecognitionSession.recognizeAgain(record:)` 用当前选中的识别服务重新识别历史条目里保存的录音，把文字写回该条目。仍失败则保留录音。

## 4. 状态

`RecordingNetworkState`（`UI/AppState.swift`）：

| 值 | 含义 | 录音条 | Typo |
|---|---|---|---|
| `normal` | 正常 | — | 正常表演 |
| `lost` | 实时流断了，录音继续 | 托盘提示连接断开 | 手放耳边听 |
| `retrying` | 正在整段重识别 | 「正在用整段录音重新识别…」 | 坚定地等 |

## 5. 测试

`Tests/Type4MeTests/NetworkResilienceTests.swift` 覆盖：错误码分类、松手后的等待规则、重识别预算、断流后继续录音并在松手后重识别、重识别也失败时的部分送达与录音保留、无任何文字时的保留、超时与关闭帧不竞争、账号类错误只结束一次，以及对应的 Typo 表情。

## 6. 已知限制

- 断流判定目前只对火山的错误码做了分类。其他识别服务的断线走各自客户端的通用失败路径，未逐个核对是否都能进入「继续录音」。
- 尚未在真实弱网环境下做完整验收。
